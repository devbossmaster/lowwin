# Phase 3 point bids

The `202609270003_accepted_bids` migration adds immutable `Bid` rows linked to the existing `Auction`, user and `Operation`. It preserves auction holds, ledger journals and their commit-time guards. A bid records its integer amount, database-stamped acceptance time, frozen terms version, disclosed fee and operation reference. `(userId, auctionId, amount)` is unique. The 100-distinct-amount limit applies per user and auction, not globally; a deferred guard reconciles `Auction.acceptedBidCount` with inserted bids.

The authenticated POST command locks the auction row, then the wallet advisory key, then uses the existing hold guard. After waiting for the auction lock it reads the database clock and checks the published `[startsAt, endsAt)` window and immutable terms. A database insert trigger stamps time again after any lock wait and repeats the window, term and cap checks. One transaction inserts the bid, increments the count, reserves only any increase above the previous maximum, transfers each entry fee to platform FEES with balanced postings, and stores an immutable idempotent receipt. Identical keys replay the receipt even after close; changed payloads fail. Rollback removes every part. Clients supply only an amount and UUID key.

`/api/auctions/[slug]/bids`, `/api/wallet` and `/api/my-bids` require a verified Better Auth session and return private no-store responses. Public catalog queries remain allowlisted and contain no live amounts, frequencies, bidder identities or winning hints. The auction form confirms the point amount, old/new maximum hold, extra reserve, fee, newly unavailable points and remaining submissions; wallet and My Bids show real journal and own accepted rows. Top-up, closing, winner selection, cancellation settlement and withdrawal are outside this phase.

DEMO bid acceptance requires local/test mode, a loopback database named `*_test`, no Vercel flag and a non-production Node environment. Production DEMO bids are rejected. The fixed Phase 2 seed schedule is never reset; bid tests create fresh, explicitly DEMO fixtures in a separate disposable loopback database.

The Phase 3 migration was applied to disposable loopback databases `lowin_bid_test` and `lowin_browser_final_test`; the existing test suite also applied it to the disposable `lowin_catalog_test` database. The repository `.env` points to a remote Supabase pooler; it was identified before migration and was not changed or migrated. Real Telegram clients and production Supabase runtime roles/RLS remain unverified.

Typecheck and the production build passed.
