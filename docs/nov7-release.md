# Lowwin public entry, bid orders and direct checkout

New bid payments and standalone top-ups use Lowwin's own checkout: payment phone and eligible provider, followed by the authorization method returned by Chapa and server-confirmed fulfillment. OTP is shown only for `auth_type: OTP`; USSD methods use the provider's phone prompt. Historical hosted orders retain their original verification and return paths.

The checkout uses one phone-and-provider panel with a fixed `+251` prefix, visible provider logos and an amount-specific Pay button. A USSD response replaces that panel with phone-approval instructions in the same sheet; there is no code/PIN input or hosted navigation on that path. The native provider/SIM prompt is controlled by the wallet and device, not imitated by Lowwin. Completion is still based on server verification.

Payment phone entry is manual and appears above the method choices in both bids and top-ups. The methods API no longer reads or returns the account phone for autofill. Shared client/server checks normalize local and international formats, require the Safaricom `7` prefix for M-Pesa and the `9` prefix for telebirr, and allow either for CBE Birr/eBirr, following [Chapa's published wallet definitions](https://github.com/Chapa-Et/inline.js/blob/main/lib/inline.js#L30-L50). These checks validate format and wallet prefix; the provider still determines whether the account is registered and authorizes payment.

Structured direct-initialization validation rejections show “Checkout could not start” with correction guidance, rather than a continuing approval spinner. This includes historical pending rows that already contain a recorded request rejection. Such requests are not automatically initialized again. Unknown/timeouts/conflicts remain attached to the original intent for reconciliation; a later authoritative payment outcome always takes precedence over old initialization errors.

Native USSD approval uses a phone icon rather than an endless activity spinner. After 90 seconds it shows the quieter long-wait view while bounded status checks continue. Cancellation/failure reported by the owned server stops approval and invalidates payment-attempt history; a slower old pending response cannot reopen it. A late verified success still reconciles normally. Closing a native prompt alone never fabricates a financial outcome. Authenticated webhook work goes directly to verification without repeating the USSD validation poll; normal USSD polling retains Chapa's validation step and uses a stable 15-second provider cooldown during the authorization window.

Chapa support confirmed this merchant dashboard currently signs `HMAC(secret, secret)`. Keep the existing explicit `CHAPA_WEBHOOK_SIGNATURE_PROFILE=legacy_secret` for those deliveries; do not send that secret/signature to the browser or auto-fallback between profiles. This reusable proof does not authenticate the body, so event fields remain lookup hints only and credit still requires authenticated v2 verification of the original payment, environment, references, principal amount and currency. The `raw_body` profile remains available for accounts that deliver the documented payload HMAC.

The bid sheet keeps one dialog through entry, payment and receipt. Its product image, description, fee and countdown sit above bid-amount entry and four separate choices: telebirr, CBE Birr, M-Pesa and Lowwin Wallet. Add amounts with the plus control; a valid amount still in the input is included. The total updates using exact cents, with one eligible coupon discounting one entry. A payment phone field appears only for an external method; wallet top-up remains a separate action.

The fee and total-bid count share the first summary row; the animated countdown has its own labeled row so Amharic labels and timer tiles cannot cover the price on narrow screens. Profile joins its owner profile, contact and counts into the existing snapshot: the base path uses three SELECTs instead of eight when optional details are enabled, excluding the unchanged referral overview. Transactions prefetches the intended page through the existing private-cache budget and loads its payment-detail code only on opening a record. These are query/code-loading reductions, not a production latency guarantee.

Pay obtains an immutable server quote and submits the selected method from the same explicit action, without a separate review screen or second provider picker. If the server total differs from the displayed total, the updated amount requires another explicit confirmation. Methods retain their selected identity and are disabled outside the merchant's supported limits. An interrupted wallet response retries the original batch even if the balance, bid limits or auction state have since changed; it does not create a replacement charge. Quotes and per-line coupon allocations remain immutable server records. A batch uses one external payment and accepts every entry atomically, or preserves the entire verified principal in the wallet when acceptance is impossible. Financial responses arriving out of order cannot replace a confirmed state with an older pending/OTP state.

Public catalog/results/rules/tutorial content renders independently of Telegram account bootstrap. Registration is dismissible and explicitly requests native contact consent; only committed bot own-contact evidence registers an account. Public query snapshots survive login while private reads and financial drafts clear on logout/account changes. Home keeps its wallet/help toolbar; Profile contains Notifications. Intro video code/media loads on demand. Recorded views and isolated split-flap timers reuse the existing activity and server-clock rules.

## Setup after review

1. Apply the additive `202611070001_direct_charge_batches` migration with the migration-owner connection: `npm run db:migrate`. Existing payment/ledger rows are retained. The normal `npm run build` generates the updated Prisma client.
2. Verify the existing protected Chapa TEST configuration on WEB and the Chapa worker. The merchant methods response must explicitly support direct charges for the intended ETB/Ethiopia rails. No browser key or payment widget is introduced. The only optional new deployment variable is `CHAPA_DIRECT_EBIRR_ENABLED=false`; leave it disabled unless merchant support is confirmed.
3. Redeploy the same reviewed source to WEB, the bot command worker (`npm run worker`), notification worker (`npm run worker:notifications`) and payment worker (`npm run worker:chapa`). Keep new/live payments disabled until merchant TEST acceptance is complete. Native contact confirmations use the existing durable notification outbox.
4. Run merchant TEST acceptance for actual USSD/OTP where supported, signed webhook delivery and duplicate/out-of-order events, app closure/restart, original-payment recovery and account isolation. Confirm one credit and the correct complete bid batch. Automated tests in this change do not initiate live charges or change production balances.
