# Verify.et migration review packet

The application migration does not itself activate payments, migrate production, register a real webhook, send a message, or make a transfer. Keep `PAYMENTS_LIVE_ENABLED=false` until production verification is complete.

## Flow and authoritative limit

The customer chooses Telebirr or CBE, pastes a reference/SMS/official receipt link or uploads a screenshot, and confirms the extracted reference. Lowwin scans images locally with Sharp/Tesseract, discards the image, and sends a JSON identifier and the frozen server-side receiving account to Verify.et. The customer never supplies an amount. A completed response can credit only when bank, identifier, ETB amount, original transfer timestamp, eligible policy window, unclaimed aliases, and receiving-account evidence match. The credit, alias claim, journal and alert are one database transaction.

**Masked receiver rule:** the [documented completed response](https://verify.et/docs/api) shows a masked `receiverAccount`. Lowwin accepts that response when Verify.et explicitly reports `settlementAccountMatch.matched=true` for the exact frozen receiving account, reports no ambiguity, and the visible receiver digits agree. The complete transaction response must also supply the original transfer timestamp, amount, bank and reference. A success badge, webhook or status response alone never credits. Masked visible digits cannot provide the same certainty as a complete receiver value; this is the residual risk of using the provider's documented match assertion. Check a real completed response from the production account before activation.

The worker polls authenticated status and replays the same `Idempotency-Key` for complete evidence. It never fetches a provider-returned URL. A queued response or webhook alone cannot credit. Callbacks are signed, deduplicated, persisted, and correlated by provider request ID; an early callback wakes the bound request after the submit response arrives.

## Observed Telebirr currency contract gap (2026-10-01)

The production Lowwin log for one HTTP 200 check reported a completed `data[0]` item but Zod `invalid_type` at `data.0.currency`. The old diagnostic wrote `received: "invalid"`, so the retained log cannot establish whether the API field was absent, null or another non-string type. The Verify.et dashboard screenshots show ETB for a Telebirr receipt and its raw source data, but the displayed detail's request ID does not match the failing log's hashed request tag. Those screenshots do not establish the exact `data[0]` response that Lowwin received. No raw API body was retained, and no paid verification was submitted to investigate.

A subsequent production log provided by the Owner confirms `data.0.currency` was **missing** for request tag `c1cc5bb9e96d` (HTTP 200, 867 ms, `CURRENCY_UNPROVEN`). This establishes the omission at the expected API path; it does not establish whether currency exists elsewhere in that response. Verify.et must supply proven currency in its completed Telebirr API result or confirm an authoritative alternate response path before Lowwin adds a mapping. The same logs report `referencesAgree: false` for two OCR passes: having one candidate in each pass does not mean the two references are identical. Manual reference entry remains available, but it cannot resolve the independent provider currency omission.

The [official completed-response contract](https://verify.et/docs/api) shows `currency: "ETB"` as a string. Lowwin now records only the safe type (`missing`, `null`, `string`, `number`, `boolean`, `array` or `object`) for invalid fields. A missing or non-string currency returns `CURRENCY_UNPROVEN` and remains in review; another string returns `CURRENCY_MISMATCH` unless it is exactly `ETB`. Neither the bank, the dashboard display nor a raw receipt's currency silently fills a missing API field. If a future existing verification reveals a documented alternate API field, review that exact structure before adding a mapping; otherwise ask Verify.et to correct its standardized response. Do not create another verification just to inspect a result. Once an authoritative completed response includes all required evidence, an eligible retry of the same deposit can credit it once and resolve its ordinary review case in the same database transaction.

## Configuration and rollout

1. Deploy the reviewed application with `VERIFY_ET_SCHEMA_READY=false` (the default), then apply additive `202609300007_verify_et_queue` with the migration role. Even if Coolify automatically deploys `main` while the older `PAYMENTS_LIVE_ENABLED=true` remains in its environment, the new gate disables submissions and verification-worker access to new tables until explicitly switched on. Preserve old `CHECK_ET` rows as immutable history; no Check.et network adapter or active credentials remain. The migration adds request, webhook and transfer-alias tables and broadens receipt constraints for new `VERIFY_ET` rows.
2. Give **web** and **notification worker** a private `VERIFY_ET_API_KEY` scoped to `verification:read` and `verification:write`. Give both `VERIFY_ET_WEBHOOK_SECRET` from the Verify.et dashboard. During planned rotation, add `VERIFY_ET_WEBHOOK_SECRET_PREVIOUS` for the documented 24-hour overlap, then remove it. The web resource keeps `RECEIPT_OCR=tesseract`; the notification worker processes queued checks even after browser closure.
3. Register `https://lowwin.shop/api/payments/verify-et/webhook` in the Verify.et dashboard for `verification.completed`. Send a signed test; expect HTTP 204 and no credit. Do not supply a per-request callback URL. Verify.et image processing is unused; verification credits still apply.
4. Confirm exact published Telebirr/CBE accounts, limits and the original transfer window. Run database reachability, zero wallet reconciliation drift, OCR/manual reference fixtures, signed webhook fixtures, queue recovery and browser checks on a disposable loopback `_test` database. Check the web and notification-worker logs for safe outcome codes, and inspect unresolved reviews.
5. After the migration is confirmed on production, set `VERIFY_ET_SCHEMA_READY=true` on both web and notification worker and redeploy them. Keep `PAYMENTS_LIVE_ENABLED=false` until a real Verify.et result confirms the receiver-match decision and original transfer timestamp, then make a controlled activation decision. The migration itself does not enable credits.

Legacy unresolved `CHECK_ET` deposits retain their frozen account and eligibility window and can be rechecked with Verify.et if not rejected, protected, expired or already claimed. Credited legacy claims, journals, balances, receipts and audits remain untouched. Cross-provider aliases share the same claim tables. A rollback is the previous application revision after disabling the live funding gate; preserve the additive migration and all financial rows. An older application will not process new Verify.et jobs, so pause new submissions and finish or investigate in-flight requests before an application rollback.

## Review evidence

Validation used disposable loopback `_test` databases and local Verify.et/notification fixtures only. The additive migration applied to a fresh local database. The focused payment suite passed 34 tests across 6 files, with zero skipped. Three targeted mobile browser runs passed with clean server shutdown: 360px OCR to credit and unreadable-image fallback, the same flow at 430px, and 360px review retry to credit with attention-queue removal and zero reconciliation drift. Typecheck and `git diff --check` passed. The production build passed with `next build --webpack`; the worktree's shared `node_modules` junction makes the default Turbopack workspace-root detection fail before compilation. No live Verify.et response, real transfer, production database or Telegram device was tested. The current provider documentation is [API reference](https://verify.et/docs/api), [getting started](https://verify.et/docs/get-started), and [REST examples](https://verify.et/docs/sdk).
