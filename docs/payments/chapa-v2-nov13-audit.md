# Chapa v2 checkout audit — 13 November 2026

The current shared bid and deposit checkout already uses Chapa v2 Inline REST with Lowwin's own UI. This audit used the official documents below and local source. No provider API, live payment, or production database was accessed.

## Documented protocol

- [Inline Charge](https://docs.chapa.global/docs/v2/integrations/inline-js): the documented public-key endpoints are `POST /v2/payments/inline` and `/inline/validate`. There is no documented v2 JavaScript SDK, script URL, widget, or callback API. Initialization uses integer cents, top-level `mobile`, and a stable `Idempotency-Key`. Validation uses the original `chapa_reference`, the same method, and an OTP only when requested. Validation does not establish money received; private verification remains required.
- [Initialize Direct Charge](https://docs.chapa.global/docs/v2/direct-charge/initiate-payment): private-key `/payments/direct` uses nested `customer` and `metadata`. Save the original authorization reference and request ID; an initialization envelope saying `success` does not mean payment completed.
- [Validate Direct Charge](https://docs.chapa.global/docs/v2/direct-charge/authorize-payment): `/payments/direct/validate` polls USSD or submits a requested OTP. It is not idempotency-cached. Never regenerate the reference, automatically replay an OTP, or collect a wallet PIN in Lowwin.
- [Verify Payments](https://docs.chapa.global/docs/v2/integrations/verify-payment): use the server's private key at `/payments/{paymentReference}/verify`. Fulfillment requires `data.status === "SUCCESS"` and the expected merchant reference, principal amount, currency, account/environment binding, and final provider reference. Redirects and validation responses cannot replace this check.
- [Webhook Overview](https://docs.chapa.global/docs/v2/integrations/webhooks): authenticate the exact raw body with HMAC-SHA256 and a constant-time comparison, durably record deliveries before acknowledging, and process retries idempotently. The configured `legacy_secret` compatibility profile is explicit and remains a lookup hint only; this work does not change signature policy.
- [Payment Webhooks](https://docs.chapa.global/docs/v2/webhooks/payment): payment event fields are top-level and lowercase. A `payment.success` delivery triggers private verification; it cannot issue credit itself. Other lifecycle notifications include failed, cancelled, incomplete, auth-needed, and blocked.
- [Error Codes](https://docs.chapa.global/docs/v2/error-codes): branch on HTTP status plus `error.code`, never arbitrary `message` text. Generic `INVALID_FORMAT` does not distinguish a phone format error from every unsupported-method/account case. Preserve only exact allowlisted structured reasons for specific PIN, OTP, funds, or registration feedback; otherwise use a clean generic explanation.
- [Security Guide](https://docs.chapa.global/docs/v2/security/security-guide): keep private keys server-side, verify before fulfillment, bind environment/reference/amount/currency, and discard OTP values after submission. Keep ledger credit and fulfillment idempotent.

## Local findings and changes

1. The merchant method catalog already has a five-minute cache and shared in-flight reads bound to configured credentials. Replacing it would add complexity without removing an observed delay.
2. Owned status reads already advertise a two-second refresh, independently of provider throttling. The avoidable delay was the fixed fifteen-second provider refresh during a new authorization. Pending active authorizations now use a five-second server cooldown for their first minute, then the existing fifteen-second cadence. Lease ownership, request throttling, and recovery/error backoff remain in force.
3. USSD refresh previously ran even after a privately verified terminal outcome. Terminal attempts now skip the stale authorization refresh and still perform private verification, allowing a late verified success to reconcile. `expiresAt` has no source marker and may be a locally assigned default; passing that display deadline alone does not disable validation or declare failure.
4. Client requests previously timed out after fifteen seconds even though Inline validation can take fifteen seconds followed by private verification taking ten seconds. Only the owned status and explicit authorization POST endpoints now receive thirty seconds. Creation/read defaults and explicit caller timeout overrides remain unchanged.
5. Validation remains before private verification because it refreshes provider state. Parallelizing those calls could read the state before validation finishes. Webhook-triggered verification already skips that extra refresh and acknowledges durable receipt before provider HTTP.
6. Real PostgreSQL coverage found that the existing evidence parser accepted verified `EXPIRED` but the saved provider-status constraint did not. The additive migration aligns that non-paid lifecycle value, preserving all verified-credit requirements.
7. When a newer success webhook arrived after an earlier verified incomplete result, a temporary private lookup failure incorrectly let the worker mark that new hint processed using the old result. The worker now retains the queued event on `verificationUnavailable`, preserving earlier evidence while retrying the new hint. A recovered private success still credits once.

## Validation

Focused unit coverage checks first-minute and later cooldowns, throttled reads, concurrent lease ownership, terminal/expiry validation guards, private late-success reconciliation after a concurrent credit, and twenty-five-second successful status/authorization responses within the bounded thirty-second client budget. Existing authorization-feedback and foreground-polling suites also pass. Production timing and real wallet behavior still require deployment/device/provider validation.
