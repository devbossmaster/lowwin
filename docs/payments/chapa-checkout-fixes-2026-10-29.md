## Confirmed findings and fixes

- The original bid form retains its number and Wallet/Chapa choice. **Pay** sends a Chapa payment directly to the hosted checkout; no second mandatory **Continue to Chapa** stage is required. Top-ups use the same direct handoff. Private top-up history exposes **Resume** for the original checkout UUID and URL, with purpose filtering before the existing 20-record limit so newer bid payments cannot hide it.
- An interrupted bid initialization persisted an intent but no checkout ID. Reopening selected payment status while clearing the transient error, leaving no recovery control. The status now exposes **Resume checkout**, which retries the saved body and original key. This also covers a normal `202` containing an ID but no checkout URL, without depending on worker repair. Ambiguous `5xx` responses retain the key even when their generic error code is `PAYMENT_UNAVAILABLE`; only known pre-commit `4xx` rejections can clear a new intent. Closing, reopening, double-clicking and retrying do not generate a replacement payment. Top-ups retain the same frozen amount and key. Account/surface epochs guard errors, state updates, navigation and in-flight locks as well as successful responses.
- Verification previously required `lowwin_attempt` whenever any metadata object was returned, even though the minimal request sends no metadata. Expectations now come from the immutable initialization. Minimal requests accept omitted, null, empty or unrelated object metadata; explicit conflicting attempt IDs fail. Historical returned metadata must match its expected fields. Omission remains accepted as before because Chapa verification treats metadata as optional. Null is normalized for signed webhook hints too. Malformed nonobject metadata is rejected.
- Actual merchant TEST responses exposed nullable customer fields on unpaid checkouts. Response parsing accepts those absent values without adding customer fields to initialization or weakening amount, currency, merchant reference, mode or final-success checks. Pending verification still cannot credit funds.
- Historical TEST checkouts can contain the hosted session token in the payment-reference field. An authenticated final-reference webhook may queue the same guarded server verification for that recognized session; the exception does not apply to a conflicting final reference or live payment. Queueing never establishes payment success.
- Confirmation previously chose invalidation scopes from the hook's screen name. It now uses the authoritative order purpose and auction slug, including the return page and paid but unaccepted late bids. Wallet, payment history, My Bids, profile, auction and referral resources refresh as appropriate. Pending states and return parameters do not invalidate as financial success, seed balances or accept bids. Unrelated auction caches and other identities remain isolated.
- External return links carry only `chapa_<checkout UUID>` through the existing Telegram bot `/start` flow. After authenticated ownership lookup, the return screen restores the original auction bid form or the Profile top-up modal from the authoritative payment purpose and auction context. The bot reports a credited amount or accepted bid only from an owned, bot-bound committed receipt and terminal database outcome; TEST confirmations are labeled. Its **Open Lowwin** or pending **Check payment** button uses that same owned return route. No payer phone, amount, result or user ID is carried in the link, and status/verification APIs continue to enforce ownership.
- The provider request remains the working minimal integer-cent amount, ETB currency and immutable merchant reference with its original idempotency key. A separate, guarded TEST initialization trial added only the documented HTTPS `return_url` and returned **HTTP 500 / `PROCESSING_FAILED`**. Its request was frozen privately before HTTP; no application intent, completed payment or ledger entry was created. Runtime optional callback/return fields remain omitted and existing intents remain unchanged. Returning through the original open Mini App or owned bot link is supported; automatic provider redirection remains unproven.

## Measured work and timing

Request-scoped `Server-Timing` now separates `auth`, `database`, `initialize`, `verify`, aggregate `checkout` and `total`. Authentication and provider HTTP stay outside the ledger transaction; transactional reauthorization, leases, advisory/row locks, exact successful evidence and exactly-once accounting remain required. Financial responses retain private `no-store` headers.

The controlled loopback benchmark used three measured iterations after warm-up, PostgreSQL and a mocked provider with 40 ms initialization / 30 ms verification delay. It excludes HTTP authentication, remote database/network latency and physical Telegram. Query events include transaction statements. Actual provider webhook authentication remains blocked. Two callbacks uniquely correlate to those confirmed payments, but their `x-chapa-signature` matches `HMAC_SHA256(secret, secret)` rather than the documented `HMAC_SHA256(secret, raw HTTP body)`. Re-saving the dashboard secret did not resolve it; the deployed configuration matches the protected local setup. The endpoint correctly returns 401. No legacy-signature fallback was added. Chapa must correct or clarify this v2 signing contract before authenticated delivery and real duplicate-delivery acceptance can pass. The separately verified merchant GET response, not either callback, authorized the payments.

Those callbacks also contain `merchant_reference: null`; their amounts are 1029 and 10288 for verified payments of 1000 and 10000 cents. The reason for that amount difference is unconfirmed. The focused follow-up normalizes only a null optional merchant hint, so a correctly authenticated unmatched event can be durably recorded and deduplicated without locating, queueing or crediting a payment. It does not alter the reported amount or strict final merchant verification. Raw bodies, signatures and payer data are excluded from this PR; recorded findings contain only sanitized evidence.
