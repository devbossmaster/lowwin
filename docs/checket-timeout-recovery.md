# Check.et timeout recovery

Check.et may finish a verification after Lowwin's request times out. A later `POST /verify` then returns `duplicate: true`, and an ordinary duplicate remains under review. Lowwin now checks the original record with Check.et's read-only `GET /verifications/{id}` when the same funding request has a recorded provider outage for that reference.

Recovery requires the original Check.et record to come from an API verification near the Lowwin timeout, within the saved funding window. The duplicate response must still contain the exact official transfer evidence: channel, reference, amount, ETB currency, completed transfer type, full receiving account, and transfer date. The original record must agree with that receipt. A database lock and the unique payment claim prevent a second credit for the same channel and reference. Missing or conflicting evidence stays in review; a dashboard row or screenshot alone cannot issue credit.

An eligible user retry can recover before the request expires. Staff can use **Payments → Deposits → request → Recover a timed-out verification** within seven days of expiry, with fresh MFA and an investigation reason, while the request remains within its attempt limit. This action asks Check.et again and credits only if the original API record passes every guard. It cannot override a wrong recipient, amount, date, currency, missing original record, or an existing claim.

There is no schema migration or new secret. Release the reviewed application version to the web service; workers do not run this path. After deployment, review the affected request's masked reference, saved receiver and amount, prior `PROVIDER_OUTAGE`, and Check.et's original verification. Use the recovery action once and inspect the immutable balance receipt, `PaymentClaim`, one credit outbox event, and `npm run wallet:reconcile`. If it remains `NEEDS_REVIEW`, investigate the recorded reason rather than repeating the action or manually altering balances. Roll back to the previous application revision if recovery behaves unexpectedly; existing claims and journal entries remain permanent and must be handled through the audited reversal flow.

Local verification: 348 unit/database tests passed, including exact duplicate recovery with one claim, journal and notification; 16 payment browser tests passed with clean server shutdown; typecheck, production build and `git diff --check` passed. These used local Check.et response fixtures and disposable PostgreSQL databases. They do not establish that the current live ETB 30 or ETB 10 transfers have a matching original API verification, nor that either wallet has been credited. Do not submit the same real transfer as a new deposit while it is under review.

API references: [Verify](https://docs.check.et/api-reference/verify), [Get verification](https://docs.check.et/api-reference/get-verification), [Error handling](https://docs.check.et/guides/error-handling).
